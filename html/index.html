Insights Forge

An AI assistant that helps Dynatrace consulting teams turn messy reliability problems into structured analyses and polished leadership deliverables — with you in control at every step.

Core purpose

Structure & accelerate

Takes a vague problem description and helps you organize it into a clear breakdown, prioritized theories, and polished reports your leadership can act on.

What it never does

No live system access

Never writes or runs queries against your Dynatrace environment. Never touches production. Your team handles the actual data lookups and configuration changes.

Guardrail

You decide what happens next

Every phase ends with a checkpoint. The agent presents its work and waits. Nothing moves forward without your explicit go-ahead.

How it works

🔒
Step-by-step with approval gates
Work happens in four phases. Each phase must be explicitly approved before the next one starts — no skipping ahead.
🚫
Thinks, doesn't touch
The agent reasons about your data and describes what to look for — but it never runs queries or touches live systems. That stays with your engineering team.
🔍
Honest about what it doesn't know
When data is missing or a hypothesis can't be validated, the agent says so plainly instead of filling the gap with guesswork.
📐
Clean, complete problem structure
Issues are broken down so that all possible causes are covered and none overlap — a technique called MECE. Every theory must be testable with a clear pass/fail signal.
🎯
Clear success criteria upfront
Before pursuing any theory, the agent pre-agrees what "confirmed," "ruled out," and "inconclusive" look like — so the investigation has a defined finish line.
🗣️
Every session starts with the problem
"Describe the problem you're trying to solve." — the agent never assumes what the issue is before you explain it.

Phase 1

Diagnose

Four sub-deliverables produced in sequence. Each feeds the next. The full Phase 1 gate fires after all four are complete.

1a — issue-tree.md → 1b/c — hypotheses.md → 1d — signals-map.md
🌲
1a — MECE Decomposition
Build mutually exclusive, collectively exhaustive issue tree
▾
  1. Restate problem as a question (not a statement)
  2. Identify axis of decomposition: system layer / user journey / team boundary / time
  3. Draft 4–7 branches — problem spaces, not solutions or conclusions
  4. For each branch, write "what we'd see if this is the cause"
  5. Check pairs for overlap; rename/restructure if found
  6. Check set for gaps: third-party, biz process, instrumentation, deploy, data quality
  7. Verify all branches are at the same abstraction level
  8. Invoke MECE lens for independent critique
  9. Revise based on lens output; write to issue-tree.md with version history
💡
1b/c — Hypothesis Generation + ICE Scoring
Testable claims per branch, scored and ranked
▾

Generation (1b)

  1. For each branch, draft 2–4 candidate hypotheses — specific, testable claims
  2. For each hypothesis, write: Expected signals · Validation approach · Required metrics · Status (open)
  3. Flag instrumentation gaps explicitly
  4. Verify each hypothesis has falsifiable exit criteria

ICE Scoring (1c)

ICE = (Impact × Confidence) / Effort

Each dimension scored 1–10. Rank descending. Flag where one dimension carries most weight.

  1. Score Impact: business outcome magnitude (1–10)
  2. Score Confidence: strength of prior evidence (1–10)
  3. Score Effort: engineering/analytics cost (1–10)
  4. Compute ICE, rank descending
  5. Invoke ICE lens for scoring validation
  6. Update hypotheses.md with scores; preserve prior scores if changed materially
🔗
1d — Signal Mapping
Technical signal → UX outcome → business KPI chains
▾
  1. List SLIs/SLOs relevant to each hypothesis
  2. Map each SLI to a user-visible UX outcome
  3. Map UX outcomes to business KPIs; quantify if possible
  4. Flag instrumentation gaps explicitly where chain is broken
  5. Verify each layer connects to the next
Output sections in signals-map.md: SLIs/SLOs · UX outcomes · Business KPIs · Instrumentation gaps
🔐
Phase 1 gate — fires after all three deliverables are complete
Approve → Phase 2 Redirect → revise artifacts Iterate through lens → MECE / Optimist / Skeptic / ICE
Phase 2

Solution — Action plan

Translate the ranked diagnosis into investigation actions, recommended actions, decision asks, and documented risks.

Inputs

hypotheses.md signals-map.md current-context.md dynatrace-playbooks.md frameworks.md stakeholder-profiles.md environment.md

Procedure

A deliberate order — MECE lays out the opportunity space, the plan is drafted against it and against the client's real instrumentation, a persona council deliberates over 2–3 rounds, the agent reconciles, then ICE re-ranks. The sequence is the point.

  1. MECE on the opportunity set — invoke MECE lens
    Lay out the full set of levers the plan could pull; check it is collectively exhaustive and mutually exclusive. This is the candidate pool.
  2. Draft the plan — investigation actions (with confirmed / ruled-out exit criteria), recommended actions, decision asks, risks + mitigations
    Ground every action in environment.md — if the client lacks the instrumentation, rewrite it as an instrumentation work item or flag the dependency. Never recommend instrumentation the client lacks.
  3. Convene the persona council — over 2–3 rounds Skeptic Optimist Customer Consultative
    Round 1 — independent positions, in parallel and blind. Round 2 — each reacts to the others. Round 3 — only if a material tension survives Round 2: each converges and flags what it won't concede (skipped when the panel has already converged; more rounds if still moving). Each panelist is grounded in the client's real instrumentation.
  4. Agent reconciles — rules on every material disagreement
    Logs each ruling in the plan's "Tensions resolved" subsection rather than averaging it away; folds Skeptic's "questions a leader will ask" into the decision asks.
  5. ICE re-ranks — after the council — invoke ICE lens
    Re-scored to execution semantics (Confidence = likelihood it executes; Impact = magnitude if the mitigation lands). The post-council ranking is what lands in the plan.
  6. Revise and write to action-plan.md

action-plan.md sections

Investigation actions

What to measure, against which data source, with pre-agreed exit criteria

Recommended actions

Ranked by impact vs effort; each conditionally gated on evidence

Decision asks

Named leaders, named decisions — not open-ended questions

Risks & tradeoffs

Each risk has a cost and a mitigation. Never buried in a separate appendix.

Tensions resolved

Each council conflict: the claim in dispute, each side's logic, and the agent's ruling. Required, not optional.

🔐
Phase 2 gate
Approve → Phase 3 Redirect → revise plan Iterate → any of the six lenses on demand
Phase 3

Deliver

Two deliverables: a leadership-ready written brief (one-pager) and a PowerPoint deck. The deck is only generated after explicit one-pager approval.

3a — Exec one-pager (5-step orchestrator)

The exec-onepager skill runs in five sequential steps. Each step reads a reference file immediately before executing — never pre-loaded. The brand-humanizer pre-pass in Step 3 is mandatory and runs before HTML is touched.

1
Recipe selection
Reads layout-system.md. Answers three narrative questions (tension, reader need, strongest evidence) before selecting components from the catalog. Records recipe + a Why: rationale before proceeding.
2
Content draft
Reads steps/1-content-assembly.md. Produces structured labeled text for every component — no HTML yet. Plan-fidelity rules apply: no re-ranking, no new findings, no upgrading open hypotheses to confirmed.
3
Brand-humanizer pre-pass Mandatory
Reads skills/brand-humanizer/SKILL.md. Runs the full brand-humanizer on every piece of drafted copy before HTML is built. Fixes AI writing patterns (em dashes, rule-of-three, hedging) and DT voice violations (wrong product names, missing trademark symbols, passive voice). Fixing copy in structured text costs far less than fixing it in finished HTML.
4
HTML build
Reads steps/2-html-renderer.md. Builds the HTML using humanized copy and the selected recipe. Follows component patterns from layout-system.md exactly — no improvised CSS or invented color values. Writes <deliverable-name>.html and companion one-pager-YYYY-MM-DD.md.
5
Brand gate
Reads steps/3-brand-gate.md. Runs the full checklist: one-page constraint · plan fidelity · brand text rules · accessibility · sources block · handoff readiness. Not marked done until every item passes.

3b — PowerPoint deck

Only generated after explicit one-pager approval. Run via tools/pptx-generator.py with a JSON spec.

Deck structure (6 sections)

2Section divider — transition visual

Sub-agent lenses

Six narrow-job critique agents living in .claude/agents/. Each has a defined job and output format. Invoked on demand or per skill procedure.

MECE lens Haiku

When: Mandatory in Phase 1 (on the issue tree) and Phase 2 (on the opportunity set), before the work is presented.

Checks: overlap between branches · gaps (third-party, biz process, instrumentation, deploy) · mixed abstraction levels · solution vs problem phrasing

ICE lens Haiku

When: Mandatory in Phase 1 (after the signals map exists) and Phase 2 (re-rank after the persona council).

Scores I/C/E (1–10 each); produces ranked table; flags where one dimension is doing most of the work

Skeptic lens Sonnet

When: Mandatory member of the Phase 2 persona council (2–3 rounds). On demand at any other gate.

Surfaces: hidden assumptions · weak evidence (single signal as truth) · instrumentation gaps · scenarios where plan misleads · the questions a leader will ask

Optimist lens Sonnet

When: Mandatory member of the Phase 2 persona council (2–3 rounds). On demand at any other gate.

Surfaces: overly conservative plan · upside left on table · compounding benefits not named · opportunities to parallelize

Consultative lens Sonnet

When: Mandatory in Phase 1 as a framing pass on tree + hypotheses wording, and in the Phase 2 persona council (2–3 rounds). Does not run in Phase 3.

Checks: voice matches senior leader expectations · SLI/SLO/RUM terminology precise · tradeoffs surfaced not buried · vendor-neutral where possible

Customer lens Sonnet

When: Mandatory member of the Phase 2 persona council (2–3 rounds). On demand at any other gate.

Asks: does work match user experience? Which journeys are deprioritized? Are we solving the right problem vs the easiest one?

Background agent
doc-freshness-checker Haiku

Dispatched at Phase 0 start if last check >7 days ago. Re-checks all DT doc citations in long-term memory. Writes to freshness-report.md. Never modifies long-term files directly. Main agent surfaces results at Phase 0 gate.

Context isolation rule

After loading the root library, the agent establishes the active engagement (created at Phase 0, or resumed by scanning engagement-folder state: front-matter) and derives the client name from its path. For the rest of the session, all client-specific reads come only from memory/clients/<active-client-name>/. The agent never reads another client's folder, even if the user's question names one. There is no global pointer file, so two concurrent sessions for different clients can never collide.

Promotion path: client → long-term

During archive (investigation-reset), lessons-learned are surfaced. The agent may propose promoting new signal patterns or failure modes to long-term memory. Each promotion requires explicit user confirmation before the write.

Gates & controls

Every phase gate offers the same three options. The agent records every decision. No phase begins without the prior one's approval.

Gate options

Approve

Proceed to the next phase. Logged in decisions-log.md with timestamp.

Redirect

Change scope, framing, or priority. Agent updates artifacts and re-presents. Gate re-fires after update.

Iterate through a lens

User picks a lens; agent invokes it and revises before re-presenting. Same gate re-fires.

Lenses at each gate

The mandatory lenses are part of the phase procedure — they always run. On top of them, you may invoke any of the six on demand at that phase's gate.

Getting started

Everything you need to go from "just opened this folder" to running your first investigation end-to-end.

Installation

📂
Installation = open this folder in Claude Code.

Open the insights-forge/ directory in VS Code with the Claude Code extension installed. CLAUDE.md loads automatically on every session — you don't do anything to activate it. The VS Code extension is recommended so you can watch artifacts appear in the file explorer as the agent works.

Other surfaces: Claude.ai as a Project runs a partial workflow but lacks the local filesystem — phase artifacts won't persist between sessions. Use the VS Code extension or terminal for real engagements.

One-time workspace setup

Before your first real engagement, take 15 minutes to populate the root library. These are the files that make the workspace yours.

1
Terminology

Open memory/long-term/terminology.md and add acronyms or internal service names your team uses. Internal names matter most — the agent will use your team's vocabulary in all deliverables.

2
Domain knowledge — org-level slots

Open memory/long-term/domain-knowledge.md and find [team to note: …] slots. Fill in org-level operational context: which DPS capabilities your contract includes, internal tool conventions, etc. Do not put client-specific environment details here — those go in each client's environment.md.

3
(Optional) Adjust CLAUDE.md

The operating manual defaults are sensible. Adjust if your team has different preferences: default vertical, citation-freshness window, additional operating constraints. The phased workflow and memory isolation rules should not be changed lightly.

Before your first engagement with a new client

Copy memory/clients/_template/ to memory/clients/<client-name>/. The agent will populate environment.md (via environment-intake skill at Phase 0 gate) and stakeholder-overlays.md (via stakeholder-overlay skill when you name a specific leader). These files persist between engagements with the same client — you only go through intake once.

Running an investigation

1
Optional: use the Seed Prompt Generator

Open html/seed-prompt-generator-src.html in VS Code or Claude Code Desktop App. It guides you through the Phase 0 inputs and builds a structured seed prompt to paste in. Recommended for new users — skip it if you know your inputs well.

2
Open with the problem

Start with: "Describe the problem you're trying to solve." — or paste your seed prompt directly. The agent reads context-framing/SKILL.md and begins Phase 0.

3
Answer up to 9 clarifying questions

One at a time, in adaptive order. If your opening paragraph covers Q1 and Q2, the agent skips them. See the table below.

4
Approve Phase 0

Agent presents reframed engagement and writes current-context.md. Approve to proceed, redirect to adjust scope, or iterate through a lens.

Continue through Phases 1, 2, 3

Finishing an engagement

When Phase 3 deliverables are approved, close out with: "Archive this investigation." Nothing moves — the engagement folder stays put.

  1. Agent asks 4 lessons-learned questions: what worked, what to avoid, new knowledge, proposed memory updates
  2. Writes lessons-learned.md into the engagement folder
  3. Adds an outcome row to the client's README.md engagement history
  4. Any approved root library updates executed (e.g., new playbook insights)
  5. Marks the engagement state: complete in its current-context.md

Working with multiple clients

Pause

Say: "Pause this engagement and start a new one." The agent marks the current engagement state: paused — nothing moves, and any number can be paused at once.

Resume

Say: "Resume [client name]." The agent scans engagement-folder statuses, you pick one, it flips back to state: active. Client data never crosses client boundaries.

Checking where you are

Open the active engagement's current-context.md (under memory/clients/<client>/engagements/<dated-slug>/): its status front-matter (state, phase) tells you where it stands; decisions-log.md in the same folder is the full audit trail. To see all active/paused engagements, scan memory/clients/*/engagements/*/current-context.md for state.
Anything stale or wrong? Ask the agent to reframe — that's a Phase 0 redirect.
