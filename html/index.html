What this is

An agent that structures consulting judgment — and waits for yours.

Insights Forge helps Dynatrace consulting teams turn an ambiguous customer problem into a MECE diagnosis, ranked testable hypotheses, an action plan with named owners and exit criteria, and leadership-ready deliverables — in four phases, with a human approval gate between each one.

Core purpose

Structure and accelerate

Turns a vague problem description into an issue tree, prioritized hypotheses, a signal-to-KPI map, and a plan your leadership can act on. It structures engineering judgment; it does not replace it.

What it never does

No live system access

Never runs queries against Dynatrace or any production system, never generates DQL or SQL, never executes configuration changes. Your team keeps the lookups and the changes.

Guardrail

You decide what happens next

Every phase ends with a five-part gate summary and a pause. Only an explicit "approve" advances the work — "looks good" does not.

Operating principles

🔒 Explicit phases, explicit approval

Four phases, five gates (Phase 3 has two: one-pager, then deck). Nothing moves without a go-ahead, and every gate decision is logged.

🔍 Honest about evidence

When data is thin or a hypothesis cannot be validated with the instrumentation that exists, the gap is named in the artifact — never papered over with confidence.

📐 MECE structure, ranked hypotheses, named exit criteria

Every artifact is reviewable in a 15-minute leadership window. "Confirmed", "ruled out", and "inconclusive" are defined before anyone looks at data.

🚧 Out-of-scope is a hard, engagement-wide constraint

Exclusions captured at Phase 0 are pasted into every critique lens and honored in every phase — even when the excluded capability is active in the tenant.

🧭 Never recommends instrumentation the client lacks

Active capabilities are the boundary of what can be surfaced. A missing capability becomes an instrumentation gap or a named follow-on, not a recommended action.

🗣️ Every session starts with the problem

"Describe the problem you're trying to solve." The agent never assumes what the issue is before you say it.

Before Phase 0 — session init

The agent reads four long-term files and holds them all session: domain-knowledge.md, the playbook hub, frameworks.md, and the stakeholder-profile hub. Individual playbooks, profiles, and vertical drill sheets are read only when a phase needs them. Each phase's skill file is read immediately before its artifact is produced — never pre-loaded.

Then it establishes the engagement: a new problem creates memory/clients/<client>/engagements/<YYYY-MM-DD-slug>/; resuming scans every engagement's status front-matter for state: active or paused and lets you pick. The session holds that path for the rest of its life.

Phase 0

Context framing

Frame the engagement before any diagnosis. Produces a complete current-context.md with every MUST-HAVE field populated and 3–5 orientation hypotheses that are starting candidates, not findings.

skills/context-framing/SKILL.mdskills/drill/SKILL.mdstakeholder-profile hub + matched profiledrill-sheets/<vertical>.mdclient-question-bank.md
🌱
Optional entry points

Seed Prompt Generator — the browser-runnable form in html/ assembles an intake brief you paste as your opening message. /drill — the same intake, conversationally, in chat. Both emit the brief format in docs/brief-contract.md; a brief with every required field filled takes the fast path: one sharpening message instead of several rounds.

Questions — in three phases

Open questions first and one at a time, where breadth comes from; closed lookups batched, because a checklist of facts does not suffer from batching the way narrative does. The order is load-bearing: the narrative answers decide which factual probes matter and which drill sheet applies.

  1. A · Narrative funnel. Q1 customer and what they do; Q2 vertical; Q3 the C.S.I.R. frame — Context, Specific Information, Intent, Response Format. One question at a time, each answer driving the next.
  2. B · Closed drill block. Q4 tenant type (SaaS or Managed); Q5 active-capability checklist — the boundary of what can be surfaced; Q6 RUM status on the focus application; Q7 stakeholder (name, archetype, what they judge success by); Q9 engagement trigger. One labeled message.
  3. C · Vertical drill sheet. Five pre-targeted questions for the customer's vertical (memory/long-term/drill-sheets/), pruned by Q5 and the exclusions, asked in one message in place of a generic "what does the technical team care about?"

Rules that shape the conversation

Marginal-value test

An optional field is asked only if a different answer could change the issue tree, the hypothesis set, or the deliverable's framing. Skipped fields are recorded as not asked (low marginal value: …) and listed at the gate so you can say "ask anyway."

Calibration routing

Your three self-calibrations — Dynatrace consulting experience, account familiarity, customer maturity — route drill depth, council size, gate verbosity, and the plan's ambition ceiling. Recorded once in current-context.md; later phases inherit it.

Out-of-scope exclusions

Captured here and honored everywhere: pasted verbatim into every lens dispatch, subtracted from what "active capability" would otherwise allow. If honoring one narrows the plan, the gate says so.

Cross-engagement lessons

Up to three ranked matches from other engagements' tagged lessons-learned.md front-matter and hook line — never their full text, which stays inside its client folder.

Exit criteria for current-context.md

MUST-HAVE
  • Customer + vertical
  • Engagement frame (C.S.I.R.)
  • Active capabilities
  • Out-of-scope exclusions
  • Consulting objective
  • Stakeholder archetype
SHOULD-HAVE
  • Tenant type
  • RUM status (conditional)
  • Technical team priorities (drill sheet)
  • Engagement trigger

Each holds a value, "declined at gate", or "not asked (low marginal value)".

NICE-TO-HAVE
  • Prior engagement reference

Recorded only if volunteered.

🔐

Phase 0 gate. No mandatory lenses; any of the six on demand. The gate's Assumptions part names every provisional brief value, every not-asked field, and every drill-sheet question pruned by an exclusion. Approval writes the decisions-log row and sets phase: 1.

Phase 1

Diagnose

Four artifacts in sequence, each feeding the next. One gate fires after all four exist.

mece-decomposition→hypothesis-generation→signal-mapping→ice-scoring
🌲
1a — Issue tree
issue-tree.md · MECE lens mandatory
▾
  1. Restate the problem as a question, not a statement.
  2. Pick the axis of decomposition: system layer, user journey, team boundary, or time.
  3. Draft 4–7 branches — problem spaces, never solutions — all at one abstraction level.
  4. For each branch write "what we'd see if this is the cause"; add an instrumentation-gaps branch when the cause may be invisible.
  5. MECE lens critiques overlap, gaps, and mixed levels before the tree is shown; revisions are recorded in the version history.
💡
1b — Hypotheses
hypotheses.md · Consultative framing pass
▾
  1. 2–4 testable claims per branch: expected signals, validation approach, required metrics (kinds of data — never queries), status.
  2. Falsifiable exit criteria for each: what "confirmed", "ruled out", and "inconclusive" look like.
  3. Instrumentation gaps named explicitly; nothing that depends on an excluded capability.
  4. Consultative lens runs a framing pass on tree and hypothesis wording — business terms, precise SLI/SLO/RUM vocabulary, calibrated to the named stakeholder's profile.
🔗
1c — Signals map
signals-map.md · matched playbooks read here
▾
  1. List the SLIs/SLOs relevant to each hypothesis; read only the playbook(s) the problem shape matches.
  2. Map each signal to a user-visible UX outcome, and each outcome to a business KPI — quantified where possible.
  3. Every broken link in the chain becomes a named instrumentation gap; a capability that is out of scope is recorded as unavailable.
⚖️
1d — ICE scores
hypotheses.md updated · ICE lens runs last
▾
ICE = (Impact × Confidence) / Effort

Each dimension 1–10. Ranked descending. The ICE lens runs after the signals map exists and flags where one dimension carries the score.

🔐

Phase 1 gate — after all four artifacts. Mandatory lens order: MECE (tree) → Consultative (framing) → ICE (last, after the signals map). Any lever dropped for touching an exclusion is reported under "out-of-scope cost". Approval sets phase: 2.

Phase 2

Solution — action plan

Translate the ranked diagnosis into investigation actions, recommended actions, decision asks, and documented risks — grounded in the client's real instrumentation and framed in 30/60/90-day windows.

skills/action-plan-builder/SKILL.mdhypotheses.md · signals-map.md · current-context.mdenvironment.mdmatched playbooks + profile

Procedure

A deliberate order: the opportunity space first, then a draft against real instrumentation, then a council that deliberates, then reconciliation, then re-ranking. The sequence is the point.

  1. MECE lens on the opportunity set — the full space of levers the plan could pull, collectively exhaustive and mutually exclusive.
  2. Draft the plan under the ambition ceiling: ground every action in environment.md; anything the client's instrumentation cannot support becomes an instrumentation work item; at low customer maturity, transformation-level moves become named follow-ons, not recommended actions.
  3. Persona council — Skeptic Optimist Customer Consultative. Round 1 blind and concurrent (all four in one dispatch message), Round 2 cross-examination, Round 3 only if positions are still moving. Artifacts go to lenses by path; the exclusions are pasted verbatim; the Optimist also receives the ambition ceiling.
  4. Agent reconciles — rules on every material disagreement in a "Tensions resolved" section instead of averaging it away; folds the Skeptic's "questions a leader will ask" into the decision asks.
  5. ICE lens re-ranks after the council, on execution semantics (Confidence = likelihood it executes; Impact = magnitude if it lands).
  6. Write action-plan.md; present the gate block.

action-plan.md sections

Investigation actions

What to measure, against which data source, who is involved, with pre-agreed confirmed / ruled-out criteria.

Recommended actions

Ranked by impact vs effort; each conditional on the evidence that must come back first.

Decision asks

Named leaders, named decisions — not open-ended questions.

Risks & tradeoffs

Each risk has a cost and a mitigation, in the same view as the recommendation.

Tensions resolved

Each council conflict: the claim in dispute, each side's logic, the agent's ruling. Required.

Follow-ons

Transformation-level moves held back by the ambition ceiling, listed separately and unranked.

🧭

Escape hatch. The full council — all three rounds, no convergence skip — is forced for high-stakes deliverables, on your request, or when calibration routing says so (low consulting experience together with low customer maturity).

🔐

Phase 2 gate. Approve to Phase 3, redirect to revise the plan, or iterate through any lens. Approval sets phase: 3.

Phase 3

Deliver

Two deliverables with two gates. The deck is generated only after the one-pager is approved. Both are written inside the engagement folder — never at the repo root.

skills/exec-onepager/SKILL.mdskills/brand-humanizer/SKILL.mdskills/pptx-builder/SKILL.mdbrand/brand-spec.mdmatched stakeholder profile

3a — Executive one-pager (five steps)

  1. Recipe selection — reads the layout catalog and the reference one-pager; answers three narrative questions (tension, reader need, strongest evidence) before choosing components; records the recipe and a Why.
  2. Content assembly — structured, labeled text for every slot, no HTML yet. Plan-fidelity rules: no re-ranking, no new findings, no promoting open hypotheses. Terminology depth follows the calibration routing.
  3. Brand-humanizer pre-pass mandatory — removes AI writing patterns (em dashes, rule-of-three, hedging) and Dynatrace voice violations before any HTML exists. Fixing copy in text costs far less than fixing it in finished HTML.
  4. HTML render — builds <slug>-onepager.html from the humanized copy, following the reference component patterns exactly; no improvised CSS or color values; no text outside the recipe's slots.
  5. Brand gate — tools/onepager-lint.py must pass: one printed page (headless Chrome), content budget against the reference, 9px font floor, palette, heading case, no dashes, sanitized sources, no unresolved assets — plus an exclusion scan and plan-fidelity check. Then the one-pager gate.

3b — PowerPoint deck

How it is built

A spec JSON at deck-spec-YYYY-MM-DD.json is rendered by tools/pptx-generator.py on the brand template (64 layouts) into deck-YYYY-MM-DD.pptx. Layouts are chosen by content count (3, 4, or 6 icon cards; 2–6 text columns); a chart with missing data is a counted failure, not a silent slide; wave backgrounds restyle text for the dark overlay.

Deck structure

  • Title slide — problem, audience, date, presenter
  • Executive summary — problem + business impact on one slide
  • Top findings — 3–5, cards or detail slides
  • Recommended actions — table
  • Risks & decision asks — leadership questions, named decisions
  • Appendix (optional) — issue tree, signals map, ICE table
🔐

Two gates. The one-pager gate runs the brand gate and exclusion scan; the deck gate repeats the exclusion scan on the spec and the generated file. No lenses are mandatory in Phase 3 — packaging, not analysis — but any of the six can be invoked. Both approvals leave phase: 3; only investigation-reset changes state:.

Sub-agent lenses

Six narrow-job critique agents in .claude/agents/, each with a fixed output format and a "Hard exclusions" block, plus one background checker. All six lenses run on the workspace's sonnet alias; the freshness checker on haiku.

📨

Dispatch rule — one message per round. Every lens in a round is dispatched in a single message so they run concurrently, never as a chain. Artifacts are handed over by path; the engagement's out-of-scope exclusions are pasted verbatim into every prompt, because a sub-agent starts with a fresh context and knows only what the dispatch hands it.

MECE lens

When: Phase 1 on the issue tree; Phase 2 on the opportunity set.

Overlap between branches · gaps (third-party, business process, instrumentation, deploy) · mixed abstraction levels · solution-shaped branches. Open

Consultative lens

When: Phase 1 framing pass on tree and hypotheses; Phase 2 council member.

Voice matches a senior technical leader · SLI/SLO/RUM terminology precise · tradeoffs surfaced, not buried · calibrated to the named stakeholder's profile. Open

ICE lens

When: Phase 1 last, after the signals map; Phase 2 re-rank after the council.

Scores Impact / Confidence / Effort · produces the ranked table · flags where one dimension carries the score. Open

Skeptic lens

When: Phase 2 council; on demand at any gate.

Hidden assumptions · single-signal "evidence" · scenarios where the plan misleads · the questions a leader will ask. Open

Optimist lens

When: Phase 2 council; on demand at any gate.

Steelmans the plan: upside left on the table, compounding benefits, parallelization — within the engagement's ambition ceiling. Open

Customer lens

When: Phase 2 council; on demand at any gate.

Does the work match what end users actually experience? Which journeys are deprioritized? Right problem, or easiest problem? Open

Tools & hooks

What holds the agent to its rules: the constraints it never crosses, the hooks that enforce them mechanically, and the scripts that gate the deliverables.

Never, under any instruction

  • Generate DQL, SQL, or any executable query syntax
  • Run live queries or execute production or configuration changes
  • Invent metrics, SLIs, or instrumentation the client does not have
  • Read another client's folder, even when you name one
  • Advance a phase without explicit approval of the current one
  • Write to long-term memory or client overlays without confirmation
  • Surface anything that depends on an out-of-scope capability

Hooks in .claude/settings.json

  • Client isolation (PreToolUse on file tools) — locks the session to a client on its first substantive touch of that client's folder; blocks every other client's folder; per-session marker so concurrent sessions cannot collide
  • Fetch allowlist (PreToolUse on WebFetch) — only domains in tools/fetch-allowlist.txt pass; lookalike domains are held for your decision
  • Workspace conformance (PostToolUse) — every edit under skills, agents, long-term memory, tools, or docs re-runs tools/conformance-check.py
  • Session start / end — creates and cleans up the per-session client marker
  • git pre-commit — blocks a commit that fails conformance (git config core.hooksPath tools/githooks)

Context isolation, mechanically enforced

After loading the root library, the session establishes its engagement path and derives the client name from it. From then on all client-specific reads come only from that client's folder. A PreToolUse hook enforces it: the session is locked to the client on its first substantive touch (a per-session marker in .claude/session-clients/), and file-tool access to every other client is blocked.

Exactly two read-only exceptions exist: (1) at session start or resume, scanning every engagement's current-context.md status front-matter to list resumable work; (2) at Phase 0, reading other engagements' lessons-learned.md front-matter and Cross-engagement hook line. Nothing else crosses a client boundary. Switching clients mid-session goes through investigation-reset, which has you approve removing the marker.

Promotion path: client → long-term

⬆️

On archive the agent may propose promoting a signal pattern, failure mode, or playbook insight to the root library. Each promotion is a separate, explicit approval. There is no auto-promotion by design — a lesson that would improve a drill sheet or playbook goes through the same path.

Field guide

Status front-matter

state — active | paused | complete; pause and archive flip it, nothing moves. phase — the phase being entered: Phase 0 approval → 1, Phase 1 → 2, Phase 2 → 3; Phase 3 approvals leave 3. last-touched — set at every gate. A resumed engagement whose phase is stale means a gate was closed incorrectly.

Calibration routing row

One line per route that deviates from the default — drill depth, council size, gate verbosity, ambition ceiling — computed once at Phase 0 from the three analyst calibrations, so later skills inherit it instead of re-deriving it.

Hypothesis rows

A hypothesis is a specific, falsifiable claim. "Latency goes up" is not a signal; "p95 on cart-service rises step-function-like after a deploy" is. Ruled-out rows are never deleted — they are part of the audit trail.

Decision-log rows

Exactly one of approve / redirect / iterate. The rationale is captured in your words where possible — that is what makes the log useful months later. Approvals also carry the two gate writes (log row + phase:).

Templates: engagements/README.md · decisions-log.md · lessons-learned.md

Gates & controls

At every gate — Phase 0, 1, 2, and both Phase 3 gates — the agent presents the same five-part block, then pauses. It is the decision frame, not a recap of the artifact.

1
Conclusion
The single most important finding or decision from this phase, in one sentence.
2
What changed
What was produced, revised, or resolved compared to the prior gate.
3
Assumptions and confidence gaps
Every assumption you should know about and every place thin evidence limits confidence — specific to this engagement, never boilerplate. This is the part that answers "did the agent understand?"
4
Out-of-scope cost
Any lever excluded because it touched an out-of-scope capability — or "No out-of-scope items arose this phase."
5
Approve / Redirect / Iterate
The closing line: the next phase, the redirect available, the lenses you can run.
Approve

Binary. Only an explicit go-ahead counts — "approve", "go ahead", "proceed to Phase N". "Looks good", partial praise, silence, or a topic change are not approval. Two writes close the gate: a decisions-log.md row and the phase: front-matter.

Redirect

Change scope, framing, or priority. The agent revises and re-presents the same gate. Logged; phase: does not move.

Iterate through a lens

Pick any of the six; the agent runs it, revises, and re-presents. On top of the lenses each phase already runs — never a substitute.

🎚️

Verbosity follows calibration routing. Default: the full block. A "terse" route keeps parts 1 and 5 in full and compresses 2–4 to one line each. A "full" route adds a one-line "why this matters" under parts 2 and 3. No route ever omits a part — an empty part 3 hides risk.

Hard constraints (never bypassable)

🚫 No DQL, SQL, or executable query syntax, under any circumstances

🚫 No production changes or configuration updates executed

🚫 No fabricated metrics, SLIs, or instrumentation that the client does not have

🚫 No reading another client's folder, even if you name one

🚫 No advancing a phase without explicit approval of the current one

🚫 No writing to long-term memory or client overlays without confirmation

Getting started

Everything from "just opened this folder" to a finished first investigation.

Installation

📂
Installation = open this folder in Claude Code.

Open insights-forge/ in VS Code with the Claude Code extension. CLAUDE.md loads on every session — it is the operating manual. The extension is recommended so you can watch artifacts appear under memory/clients/ as the agent works; the terminal works too.

One-time workspace setup (about 15 minutes)

  1. Terminology. Add your team's acronyms and internal service names to memory/long-term/terminology.md — the agent uses your vocabulary in deliverables.
  2. Domain knowledge slots. Fill the [team to note] slots in memory/long-term/domain-knowledge.md with org-level context. Never client details — those go in each client's environment.md.
  3. Hooks and tools. Run git config core.hooksPath tools/githooks; install tools/requirements.txt into a virtualenv for the deck generator.
  4. Drill sheets (optional but high value). The eight vertical sheets ship as drafts; one session with a practitioner per vertical turns them into the instrument your consultants run in front of customers.

Before your first engagement with a new client

Copy memory/clients/_template/ to memory/clients/<client-name>/. The agent populates environment.md (environment-intake) and stakeholder-overlays.md (stakeholder-overlay, when you name a leader). These persist across engagements with the same client — intake happens once.

Running an investigation

  1. Pre-fill, or don't. Open the browser-runnable Seed Prompt Generator in html/, fill it, and paste the brief as your opening message; or type /drill for the same intake in chat; or simply answer "Describe the problem you're trying to solve."
  2. Answer Phase 0. Q1–Q3 as a conversation, the factual block in one message, then your customer's five drill-sheet questions. A complete brief collapses all of it into one sharpening message.
  3. Read the gate block, then say "approve" — or redirect, or ask for a lens. Part 3 lists what the agent assumed and what it chose not to ask.
  4. Continue through Phases 1, 2, 3. Each has its own gate and artifacts; the deck waits for the one-pager. Don't skip gates — they catch bad assumptions before downstream work bakes them in.
  5. Close. "Archive this investigation." The agent asks four lessons-learned questions, writes the tagged lessons-learned.md, adds an outcome row to the client README, proposes any long-term promotions for your approval, and marks state: complete.

Working with multiple clients

Pause

"Pause this engagement and start a new one." Marks state: paused; nothing moves; any number can be paused at once.

Resume

"Resume [client]." The agent scans engagement statuses, you pick one, it flips back to active. Client data never crosses a client boundary.

📍

Where am I? Open the engagement's current-context.md: its front-matter says state and phase; decisions-log.md beside it is the audit trail. To list every active or paused engagement, scan memory/clients/*/engagements/*/current-context.md for state. Anything stale or wrong? Ask the agent to reframe — that's a Phase 0 redirect.
