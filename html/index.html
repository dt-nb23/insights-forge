What this is

An agent that structures consulting judgment — and waits for yours.

Insights Forge helps Dynatrace consulting teams turn an ambiguous customer problem into a MECE diagnosis, a ranked set of testable hypotheses, an action plan with named owners and exit criteria, and leadership-ready deliverables. It works in four phases with a human approval gate between each one.

Core purpose

Structure and accelerate

Takes a vague problem description and turns it into an issue tree, prioritized hypotheses, a signal-to-KPI map, and a plan your leadership can act on. It structures engineering judgment; it does not replace it.

What it never does

No live system access

Never runs queries against Dynatrace or any production system, never generates DQL or SQL, never executes configuration changes. Your team keeps the data lookups and the changes.

Guardrail

You decide what happens next

Every phase ends with a five-part gate summary and a pause. Only an explicit "approve" advances the work — "looks good" does not.

Operating principles

🔒 Explicit phases, explicit approval

Four phases, five gates (Phase 3 has two: one-pager, then deck). Nothing moves without a go-ahead, and every gate decision is logged.

🔍 Honest about evidence

When data is thin or a hypothesis cannot be validated with the instrumentation that exists, the gap is named in the artifact — never papered over with confidence.

📐 MECE structure, ranked hypotheses, named exit criteria

Every artifact is reviewable in a 15-minute leadership window. "Confirmed", "ruled out", and "inconclusive" are defined before anyone looks at data.

🚧 Out-of-scope is a hard, engagement-wide constraint

Exclusions captured at Phase 0 are pasted into every critique lens and honored in every phase — even when the excluded capability is active in the tenant.

🧭 Never recommends instrumentation the client lacks

Active capabilities are the boundary of what can be surfaced. A missing capability becomes an instrumentation gap or a named follow-on, not a recommended action.

🗣️ Every session starts with the problem

"Describe the problem you're trying to solve." The agent never assumes what the issue is before you say it.

How an engagement flows

Four phases, five gates, one folder

Everything the agent writes for an engagement lands in one dated folder under the client's workspace: memory/clients/<client>/engagements/<YYYY-MM-DD-slug>/. The folder is self-describing — its current-context.md opens with a status block (state, phase, last-touched), so there is no global pointer file and two sessions for two clients can never collide.

Phase by phase

What each phase produces, asks of you, and checks

Phase 0

Context framing

skills/context-framing/SKILL.md

Frames the engagement before any diagnosis. The output is a complete current-context.md: customer, vertical, the C.S.I.R. frame (Context, Specific Information, Intent, Response Format), active capabilities, out-of-scope exclusions, stakeholder archetype, consulting objective, and 3–5 orientation hypotheses that are starting candidates, not findings.

Asks you — in three phases

  1. A · Narrative funnel. Q1 customer, Q2 vertical, Q3 C.S.I.R. — one question at a time, each answer driving the next.
  2. B · Closed drill block. Q4 tenant type, Q5 capability checklist, Q6 RUM status, Q7 stakeholder, Q9 trigger — one batched message.
  3. C · Vertical drill sheet. Five pre-targeted questions for the customer's vertical, in one message, in place of a generic "what does the technical team care about?"

Rules that shape the conversation

  • Marginal-value test — an optional field is asked only if a different answer could change the issue tree, the hypotheses, or the deliverable's framing. Skipped fields are listed at the gate so you can say "ask anyway."
  • Brief-complete fast path — a pasted seed-prompt brief with every required field filled collapses the rounds into one sharpening message.
  • Calibration routing — your three self-calibrations (experience, account familiarity, customer maturity) set drill depth, council size, gate verbosity, and the plan's ambition ceiling.
  • Cross-engagement lessons — up to three ranked matches from other engagements' tagged lessons-learned.md front-matter, never their full text.

Produces

  • current-context.md with status front-matter (state: active, phase: 0)
  • decisions-log.md opened for the engagement
  • A background doc-freshness check on cited Dynatrace docs, surfaced at the gate

Lenses

None mandatory. Any of the six on demand.

Phase 1

Diagnose

mece-decomposition → hypothesis-generation → signal-mapping → ice-scoring

Four artifacts in sequence, each feeding the next. One gate fires after all four exist.

Sequence

  1. Issue tree — restate the problem as a question; 4–7 mutually exclusive branches at one abstraction level, each with "what we'd see if this is the cause." MECE lens critiques it before it is shown.
  2. Hypotheses — 2–4 testable claims per branch: expected signals, validation approach, required metrics (kinds of data, never queries), falsifiable exit criteria. Consultative lens runs a framing pass on tree and hypothesis wording.
  3. Signals map — technical signal → UX outcome → business KPI, with every broken link named as an instrumentation gap. Matched playbooks are read here, one at a time.
  4. ICE scores — Impact × Confidence ÷ Effort, each 1–10, ranked. ICE lens runs last, after the signals map, and flags where one dimension carries the score.

Produces

  • issue-tree.md — branches, MECE check record, version history
  • hypotheses.md — status legend: open → validating → confirmed / ruled out; ruled-out rows are never deleted
  • signals-map.md — SLIs/SLOs · UX outcomes · business KPIs · instrumentation gaps

Asks you

To approve, redirect the framing, or iterate through a lens. Anything touching an out-of-scope capability is dropped and reported under the gate's "out-of-scope cost."

Phase 2

Solution — action plan

skills/action-plan-builder/SKILL.md

Translates the ranked diagnosis into investigation actions, recommended actions, decision asks, and risks — grounded in the client's real instrumentation (environment.md) and framed in 30/60/90-day windows.

Sequence

  1. MECE lens on the opportunity set — the full space of levers the plan could pull.
  2. Draft against the client's instrumentation and under the ambition ceiling: at low customer maturity, transformation-level moves become named follow-ons, not recommended actions.
  3. Persona council — Skeptic, Optimist, Customer, Consultative. Round 1 blind and concurrent (one dispatch message), Round 2 cross-examination, Round 3 only if positions are still moving. Artifacts go to lenses by path; exclusions are pasted verbatim.
  4. Agent reconciles — rules on every material disagreement in a "Tensions resolved" section instead of averaging it away.
  5. ICE lens re-ranks after the council, on execution semantics.

Produces

  • action-plan.md — investigation actions (data source, owner, confirmed/ruled-out criteria) · recommended actions (ranked, conditional on evidence) · decision asks (named leader, named decision) · risks and tradeoffs (each with a mitigation) · tensions resolved

Escape hatch

The full council is forced for high-stakes deliverables, on your request, or when calibration routing says so (low experience and low customer maturity together).

Phase 3

Deliver

exec-onepager → brand-humanizer → pptx-builder

Two deliverables with two gates. The deck is generated only after the one-pager is approved. Both are written inside the engagement folder — never at the repo root.

3a · One-pager (five steps)

  1. Recipe selection from the layout catalog, after answering three narrative questions (tension, reader need, strongest evidence).
  2. Content assembly in structured text — plan-fidelity rules: no re-ranking, no new findings, no promoting open hypotheses.
  3. Brand-humanizer pre-pass mandatory — removes AI writing patterns and Dynatrace voice violations before any HTML exists.
  4. HTML render from the humanized copy, following the reference one-pager's component patterns exactly.
  5. Brand gate — tools/onepager-lint.py must pass: one printed page, content budget, 9px font floor, palette, sanitized sources, no unresolved assets; plus an exclusion scan.

3b · Deck

  • Spec JSON at deck-spec-YYYY-MM-DD.json, generated by tools/pptx-generator.py into deck-YYYY-MM-DD.pptx from the brand template (64 layouts).
  • Layouts are chosen by content count (3 vs 4 vs 6 icon cards; 2–6 text columns); a chart with missing data is a counted failure, not a silent slide.
  • Wave backgrounds restyle text for the dark overlay; the deck gate repeats the exclusion scan.

Produces

<slug>-onepager.html · deck-spec-YYYY-MM-DD.json · deck-YYYY-MM-DD.pptx

Human-in-the-loop

Gates and the five-part summary

At every gate — Phase 0, 1, 2, and both Phase 3 gates — the agent presents the same five-part block. It is the decision frame, not a recap of the artifact: part 3 is where you find out whether the agent understood.

1
Conclusion
The single most important finding or decision from this phase, in one sentence.
2
What changed
What was produced, revised, or resolved compared to the prior gate.
3
Assumptions and confidence gaps
Every assumption you should know about and every place thin evidence limits confidence — specific to this engagement, never boilerplate. At Phase 0 this includes every optional field the agent chose not to ask.
4
Out-of-scope cost
Any lever or opportunity excluded because it touched an out-of-scope capability — or "No out-of-scope items arose this phase."
5
Approve / Redirect / Iterate
The closing line that names the next phase, the redirect available, and the lenses you can run.
Approve

Proceed. Only an explicit go-ahead counts ("approve", "go ahead", "proceed to Phase N"). Two writes close the gate: a row in decisions-log.md and the phase: front-matter set to the phase being entered.

Redirect

Change scope, framing, or priority. The agent revises and re-presents the same gate. Logged; does not move phase:.

Iterate through a lens

Pick any of the six lenses; the agent runs it, revises, and re-presents. This is on top of the lenses each phase already runs.

🎚️

Verbosity follows calibration routing. The default is the full block. A "terse" route keeps parts 1 and 5 in full and compresses 2–4 to one line each. A "full" route adds a one-line "why this matters" under parts 2 and 3. No route ever omits a part — an empty part 3 hides risk.

Sub-agents

Six critique lenses and one background checker

Each lens lives in .claude/agents/ with a narrow job, a fixed output format, and a "Hard exclusions" block. Lenses in a round are dispatched in a single message so they run concurrently; each receives artifacts by path and the engagement's exclusions pasted verbatim. All six run on the workspace's sonnet alias; the freshness checker on haiku.

State and knowledge

Memory model

Two tiers with strict isolation between client data and shared knowledge — stated in the operating manual and enforced by a hook, not just by instruction.

Root library

memory/long-term/ domain-knowledge.md · frameworks.md · terminology.md dynatrace-playbooks.md (hub) → playbooks/*.md stakeholder-profiles.md (hub) → profiles/*.md drill-sheets/ (one per vertical) client-question-bank.md · freshness-report.md brand/brand-spec.md · brand/reference/
Read freely every session. Hubs load at start; individual files on need. Writes require explicit approval. Never contains client data.

Client workspace

memory/clients/<client>/ README.md (engagement history) environment.md · contract.md stakeholder-overlays.md engagements/<YYYY-MM-DD-slug>/
Fully isolated per client. Template at memory/clients/_template/. Never read unless that client is the session's engagement.

Engagement folder

…/engagements/<YYYY-MM-DD-slug>/ current-context.md (status front-matter) issue-tree.md · hypotheses.md · signals-map.md action-plan.md · decisions-log.md <slug>-onepager.html · deck-spec · deck.pptx lessons-learned.md (tagged, on archive)
Self-describing via state: active | paused | complete and phase:. Nothing ever moves — pause and archive flip a field.

Context isolation, mechanically enforced

A PreToolUse hook locks each session to a client on its first substantive touch of that client's folder (a per-session marker, so concurrent sessions cannot collide) and blocks file-tool access to every other client. Exactly two read-only exceptions exist: scanning every engagement's status front-matter at session start to list resumable work, and reading other engagements' lessons-learned.md front-matter and hook line at Phase 0. Switching clients mid-session goes through investigation-reset, with your approval.

Promotion path, client → long-term. On archive the agent may propose promoting a signal pattern, failure mode, or playbook insight to the root library. Each promotion is a separate, explicit approval. There is no auto-promotion by design.

What holds it to the rules

Hard constraints, hooks, and tools

Never, under any instruction

  • Generate DQL, SQL, or any executable query syntax
  • Run live queries or execute production or configuration changes
  • Invent metrics, SLIs, or instrumentation the client does not have
  • Read another client's folder, even when you name one
  • Advance a phase without explicit approval of the current one
  • Write to long-term memory or client overlays without confirmation
  • Surface anything that depends on an out-of-scope capability

Hooks registered in .claude/settings.json

  • Client isolation (PreToolUse on file tools) — the session lock described above
  • Fetch allowlist (PreToolUse on WebFetch) — only tools/fetch-allowlist.txt domains pass; lookalikes are held for your decision
  • Workspace conformance (PostToolUse) — every edit under skills, agents, long-term memory, tools, or docs re-runs tools/conformance-check.py
  • Session start / end — creates and cleans up the per-session client marker
  • git pre-commit — blocks a commit that fails conformance (git config core.hooksPath tools/githooks)

Run your first engagement

Getting started

Install

Installation = open this folder in Claude Code. CLAUDE.md loads on every session and is the operating manual. The VS Code extension is recommended so you can watch artifacts appear under memory/clients/ as the agent works.

One-time setup (about 15 minutes)

  1. Add your team's acronyms and internal service names to memory/long-term/terminology.md.
  2. Fill the [team to note] slots in memory/long-term/domain-knowledge.md with org-level context — never client details.
  3. Run git config core.hooksPath tools/githooks, and install tools/requirements.txt into a virtualenv for the deck generator.
  4. Optional: validate the vertical drill sheets with a practitioner who works each vertical — they ship as drafts.

Start an engagement

  1. Pre-fill, or don't. Open the browser-runnable Seed Prompt Generator in html/, fill it, and paste the brief as your opening message; or type /drill for the same intake in chat; or simply answer "Describe the problem you're trying to solve."
  2. Answer Phase 0. Q1–Q3 as a conversation, the factual block in one message, then your customer's five drill-sheet questions. A complete brief collapses this to one sharpening message.
  3. Read the gate block, then say "approve" — or redirect, or ask for a lens. Part 3 lists what the agent assumed and what it chose not to ask.
  4. Continue through Phases 1, 2, 3. Each has its own gate; the deck waits for the one-pager.
  5. Close. "Archive this investigation" captures tagged lessons and an outcome row. "Pause" and "Resume <client>" flip the folder's state without moving anything.
